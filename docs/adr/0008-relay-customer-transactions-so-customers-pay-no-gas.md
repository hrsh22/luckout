# Relay customer transactions so customers pay no gas

Purchases were already free for customers: the server submits them (ADR-0001). Everything else a customer signs in the Web App (depositing, withdrawing, saving their Default Mode or Spending Limits, the testnet faucet, and registering for USDC before a Top-Up) was a transaction from their own wallet, paid in NEAR. A customer holding only USDC could not even make their first deposit.

These calls are now NEP-366 meta transactions. The wallet signs the call as a delegate action without sending it (`signDelegateActions` in NEAR Connect), the Web App posts it to the server's `POST /relay`, and a separate relayer account wraps it in a transaction to the customer's account and pays the gas. The network checks the customer's signature and runs the call as the customer. NEAR also charges any deposit attached to the inner call to the relayer (`total_deposit` in nearcore), so the 1 yoctoNEAR that proves a full-access signature costs the customer nothing either. The contract is unchanged: a function-call key can't attach a deposit inside a delegate action any more than outside one, so withdrawing and changing limits still need the customer's full-access key.

The relayer is its own account, not the operator's, because sending a delegate action needs a full-access key and the operator's key stays restricted to the purchase methods. It holds only gas money; a stolen relayer key can spend that and nothing else, since it can only send what customers signed. The server pays only for the Web App's own calls, each with exactly the deposit it needs: `withdraw`, `set_default_mode` and `set_limits` on our contract, `ft_transfer_call` into our contract and `storage_deposit` for the customer themselves on USDC, and the faucet on testnet. Exact deposits matter because a deposit on a failed call is refunded to the customer, so a loose cap would let anyone drain the relayer into their own account; for the same reason a second USDC registration is refused. Before paying, it checks for free what the network would refuse: the sender is the signed-in account, the key is a full-access key on that account, the nonce is unused, the approval hasn't expired, and the signature is valid. The same signature sent twice returns the first result instead of paying again. Each account gets 20 free relays a day and everyone together 500, which bounds what a bot can burn; past that, or with no relayer configured, the Web App sends from the wallet as before. A relay costs the relayer about 0.0005 NEAR (measured on testnet).

Not every wallet can sign delegate actions. NEAR Connect's manifest lists HOT, Meteor, Intear, Ledger and NEAR Mobile as able to; MyNearWallet, OKX and the Ethereum-wallet option can't, and their customers still pay their own fees. Top-Ups still cost gas on the origin chain, which no NEAR relayer can pay.

Rejected: running NEAR's reference relayer (`pagoda-relayer-rs`) as a separate service, which would add a process to deploy and configure while still needing the same allowlist; sending each new customer a little NEAR instead, which is simpler and works with every wallet but still shows a fee in the wallet, runs out, and is easy to farm with fresh accounts.

**Amended 2026-11-11.** The relayer also pays for a customer's own `reclaim` and `retry_draw` (no deposit, so nothing can be refunded to them), the Web App's buttons for a purchase left open 24 hours or a Draw whose callback failed. Each request must be the exact borsh encoding of the signed delegate (padded copies are refused, so the dedupe by hash holds), and checking the caps, the dedupe, the free checks and the send run one request at a time, so parallel requests can't all pass a cap or register USDC twice.

**Amended 2026-11-11 (EVM wallets, ADR-0011).** The note above that customers of NEAR Connect's Ethereum-wallet option pay their own fees was wrong: that option can't sign the sign-in message, so those customers couldn't get in at all. NEAR Connect now offers only wallets that can sign in, and EVM wallets sign in through their own path instead. Our relayer also sends EVM customers' signed NEAR Intents payloads to `intents.near` (`execute_intents`). It does so only one at a time, only when signed by the signed-in account, and only for intents exactly as the web app builds them: moving USDC into the signer's own Balance, one of our contract's `on_auth` actions, or sending USDC to a 1Click withdrawal this server quoted for them. Before paying, it checks the signature, the deadline and that the nonce is unused. The same caps apply, except to a Top-Up's own move-in, which an attacker can't repeat without making real swaps. On testnet the relayer also pays for an EVM customer's daily faucet.
