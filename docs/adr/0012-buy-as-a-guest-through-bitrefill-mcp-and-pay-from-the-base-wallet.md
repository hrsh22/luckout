# Buy as a guest through Bitrefill's MCP and pay each order from the Base Wallet

Until now every real card was bought on our one Bitrefill account with an API key and paid from its USD store credit (ADR-0009). Bitrefill caps an account at 15 orders a day, so every customer shared those 15. Bitrefill also told us (2026-11-13/14) that it doesn't want all cards bought under one account, because support for a bad code then can't reach the buyer, and that it is reluctant to give its Business API to partners. It offered its MCP server instead, either as a guest or with the customer's own Bitrefill account.

So, on mainnet (staging and production):

- **Guest checkout by default.** The server logs in to Bitrefill's MCP as a guest with our OAuth client (client credentials; the login lasts 6 hours and is renewed by itself). Each order carries the customer's **Checkout Email** (a throwaway one is fine), so Bitrefill's limits count per email: 15 orders a day, $500 a day and $1,000 a month. Our database counts the same limits, so the shop and the bot say "you've reached today's limit" before Bitrefill refuses.
- **Connect Bitrefill (optional).** A customer who wants higher limits logs in to Bitrefill from our site (OAuth with PKCE, through the same client), and their orders are placed on their own account, under its limits: no Checkout Email, and none of our per-email checks. They're still paid by us, the same way (`usdc_base` from the Base Wallet, never their balance), and delivery is read with the invoice's access token as for a guest. Each customer has at most one Bitrefill Connection, its tokens sealed like the email. An access token lasts 6 hours and is renewed when an order needs it. A refresh token lasts 7 days and works once, so one customer's renewals take turns and each new one is saved before use; a daily sweep renews any connection unused for 5 days, so an idle customer stays connected. If Bitrefill refuses a renewal, the connection is dropped and the card is bought as a guest with their Checkout Email, or, without one, refunded in full with a note to connect again or add an email. It's offered only where `BITREFILL_REDIRECT_URI` is set and registered with Bitrefill.
- **An API key for reading the catalog only.** Browsing, search, card logos, the popular-cards list and price lookups keep using an API key, which never places an order: every order goes through the guest login. Bitrefill keys can't be made read-only, so the key belongs to an account holding no credit (production's is spent down to $0 at the switch; staging uses the testnet account's, which holds $0). Reads create no invoices, so they use none of the order limits, and they keep the guest login's 30 MCP calls a minute for buying. Without a key, browsing would need a country for every search, and logos would stay frozen at the last copy.
- **Payment.** A guest can't use store credit. Each order is an invoice in USDC on Base (`usdc_base`), paid by an exact transfer from the Base Wallet to the invoice's address. Before paying, the server checks the token is Base USDC, the address is well-formed, and the amount is no more than the price the contract admitted. The transfer is saved before it's sent, so a retry resends the same transaction and can never pay twice. Bitrefill's x402 payment is for its separate wallet checkout, where the paying wallet is the customer, so it would pool every customer under our wallet; it isn't used. (Asked Bitrefill on 2026-11-15 whether guest invoices can be paid by x402, and whether paying them all from one wallet keeps limits per email.)
- **The Base Float is the only float.** Bitrefill credit is retired on mainnet (this supersedes ADR-0009's credit): refills only top up the Base Wallet's USDC from the Treasury. The checks that a purchase never counts on the same money twice now apply to the Base Float.
- **Delivery takes longer.** The code arrives once Bitrefill sees the Base payment, usually within a minute, instead of in about a second (amends ADR-0001). A guest invoice's price matched the store-credit price in our tests (₹50 Swiggy: 0.55 USDC both ways).

Testnet keeps its own Bitrefill account and key, because Bitrefill's free test cards can't be bought as a guest and a guest order needs real USDC on Base. Testnet now runs only on a developer's machine (ADR-0010).

Considered and rejected: one Base wallet per customer to spread Bitrefill's limits (its Terms §29.6 count creating several wallets to get around limits as a breach), and Bitrefill's x402 wallet checkout (codes only reach the paying wallet, and its limits are that wallet's).

**Amended 2026-11-25.** Bitrefill's limits (15 orders a day, $500 a day, $1,000 a month) are counted by Luckout per card over the last 24 hours and the last 30 days (`GUEST_LIMITS`, `Purchases.ts`). A guest's cards are also sent to the Checkout Email as a Bitrefill gift, so the code reaches the customer there as well as in Luckout.

**Amended 2026-11-25 (Checkout Email on a Checkout).** The Checkout Email is fixed on a Checkout when it is placed, so changing the saved address later doesn't change where that Checkout's cards go.
