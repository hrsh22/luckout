# Build on NEAR with a chat agent and prepaid balances

Luckout is built for the NEAR hackathon (development ends 2026-11-14 23:59 UTC). One NEAR contract holds each customer's Balance in native USDC on NEAR (`17208628f84f5d6ad33f0da3bbbeb27ffcb398eac501a31bd6ad2011e36133a1`), their Spending Limits and Default Mode, the immutable Game Versions, the Refund Reserve, and every Draw. Customers deposit with `ft_transfer_call` and may withdraw any unlocked Balance at any time. A Top-Up from any other chain is a NEAR Intents 1Click swap that lands USDC in the customer's NEAR account, followed by one deposit, so funds from several chains pool before any purchase exists.

Customers use two channels backed by one server. The Web App is where a customer connects their NEAR wallet, tops up, sets Spending Limits and Default Mode, browses and buys, and reads purchase history, Refunds, and Redemption Data. The Agent is a Telegram bot whose language model can search the catalog, check Balance, and buy; Telegram is chosen over X because voucher codes must be private and X write access is paid. A customer links Telegram to their NEAR account once from the Web App by signing a one-time code with their wallet; that link lives in the server database, not onchain. Every purchase from either channel is submitted by the server's NEAR account, which holds only a function-call access key restricted to the contract's purchase methods, so customers pay no gas and sign nothing per purchase. The contract enforces each customer's Spending Limits on every submission, so a fully compromised server can spend at most those limits. Raising limits and withdrawing need the customer's full-access signature. The server also sets the Reference Price; customers trust it to match Bitrefill, and every purchase records it onchain for comparison.

A purchase is either a Standard Purchase (the Normal mode) or a Lucky Buy. Fulfillment pays Bitrefill from the operator's prepaid Bitrefill account balance, so the voucher code arrives in seconds; the operator refills that balance and sweeps its proceeds in periodic batches. A Lucky Buy debits the Maximum Price from the customer's Balance and locks its largest possible Reference Discount from Free Reserve. When the voucher is delivered, the server confirms delivery onchain, and the same call runs the Draw and credits any Refund to the customer's Balance, so the code and the result reach the customer together, seconds after they buy, with no reveal animation. The confirmation is submitted before its block's randomness exists, so the operator cannot see a result and then choose to declare the purchase failed instead. The random value per purchase is `sha256(env::random_seed() || purchase_id)`, so purchases confirmed in the same block draw independently; block producers can bias `random_seed` slightly, which is acceptable only because the Discount Cap and Spending Limits bound every Draw. A Standard Purchase debits the Reference Price with no Draw and no lock. If Bitrefill fails, the operator marks the purchase failed and the full amount debited returns to the customer's Balance with no Draw, so Bitrefill refund risk sits with the operator. If the operator neither confirms nor fails a purchase within 24 hours, the customer may reclaim the full amount debited.

Every Lucky Buy commits to an immutable Game Version; new economics need a new version. Only a Final Price below Reference Price is ever called a discount or win. Voucher codes are delivered in the Web App and in a Telegram direct message, and the Bitrefill order history is the recovery path. The contract owner account may pause new purchases, which never blocks confirmation, settlement, failure, reclaim, or withdrawal.
