# Production review, 9 Nov 2026

Four independent passes: backend (server + API), contract, web code, and product/design on the live site. Each finding below was checked against the code. "Unverified" means the reviewer couldn't confirm it without a live test.

**Overall:** the core is sound. USDC conservation holds, withdrawals and deposits are safe, NEP-413 sign-in, persist-before-send signing and the Agent's prepare/confirm split all hold up, and the browser Draw recompute matches the contract bit for bit. What's missing for a real startup is (1) one contract-level fairness hole, (2) operational hardening of the purchase pipeline, (3) session and wallet edge cases in the web app, and (4) the startup surface itself: a landing page, honest odds framing, legal pages, monitoring.

## P0: before any real money

### Contract

| # | Finding | Fix |
|---|---|---|
| C1 | **Draw result-shopping.** A full-access key (owner, or the operator account's own full-access key) can send `[confirm_delivery, X]` in one transaction, where `X` panics depending on the Draw's outcome, and retry until it likes the result. Possibly also with tuned gas from the operator key alone (unverified). | `confirm_delivery` marks the purchase Delivered and schedules a `#[private]` callback with contract-set gas that runs the Draw in a later receipt. **This changes CONTEXT.md ("Draw … in the same call that confirms delivery") and the README's "No result shopping" claim; both need updating.** |
| C2 | **Upgrade power isn't disclosed.** The contract account keeps a full-access key, so whoever holds it can redeploy and take every balance. | On mainnet: delete the full-access keys on the contract and operator accounts (or put upgrades behind a multisig with a timelock), and disclose owner and upgrade powers in the Security model. |
| C3 | A stolen operator key can fill contract storage with 1-micro-USDC purchases and stop new purchases. | Minimum Reference Price (1 USDC), plus an alert on the contract's NEAR balance. |
| C4 | The limit promise says more than the contract enforces: the daily limit resets at UTC midnight (2× across midnight), the operator chooses the mode and `max_debit`, and delivery isn't proven onchain. | Rolling 24h window; disclose the rest; add the cases to `attack.ts`. |
| C5 | Missing events (`withdraw`, restore, `set_operator`, `set_paused`, owner withdrawals, limits, mode). The premium is rounded down (tiny Lucky Amounts average under 106%, against ADR-0004). Order ids aren't bound to customer and amount. | Emit an event from each; `div_ceil` the premium; store customer and debit with the order id and require them to match. |

### Server

| # | Finding | Fix |
|---|---|---|
| S1 | Unauthenticated `/catalog/:id` and `/quote` can use up the MCP quota (30/min, shared with buys). A rate-limited buy is then treated as "unknown" and the purchase sticks at `ordering` with the customer's money locked for 24h. | Treat 429/401/403 on a buy as Refused; cache failed lookups; require sign-in for `/quote`; tighter limit on `/catalog/:id`. |
| S2 | A deploy (`pm2 reload`, 10s kill timeout) or crash interrupts in-flight purchases mid-order. `void bot.start()` crashes the process on a Telegram 409. | Drain running purchases on shutdown with a deadline; make order + record uninterruptible; `kill_timeout` 120s; catch the `bot.start` rejection. |
| S3 | The reconciler retries forever, oldest first, so 50 permanently broken rows starve every newer purchase. | `attempts` / `next_attempt_at` columns, backoff, move to `stuck` after N tries, alert. |
| S4 | Telegram: one wallet can have several hidden links, and links survive Unlink. A Confirm prepared before an unlink still buys. | One link per account (replace on relink); re-check the link when Confirm is tapped. |
| S5 | Any signed-in account, even with zero balance, makes the operator sign and pay gas for 120 purchases/min, blocking real settlements behind the send lock. | Preflight `get_account` balance and limit check; cap each account's unfinished purchases; send settlements ahead of admissions. |
| S6 | Config fails open: `NEAR_NETWORK` typos turn off the testnet guard, a missing `DATABASE_URL` silently uses PGlite, plus optional secrets and an empty contract id. Nothing enforces a single instance. No timeouts on Bitrefill or 1Click calls (against ADR-0006). | Strict config, refuse to start on mainnet if anything is missing; `pg_try_advisory_lock` at startup; timeouts on every external call. |
| S7 | A refused `fail_purchase` or `confirm_delivery` is labelled without reading the chain, so the customer can be told "refunded" when they weren't. | Read `get_purchase` and record the real onchain state. |
| S8 | **Unverified, mainnet:** whether REST `GET /invoices` can see invoices created through MCP, and whether the USD balance pays the checkout price or about 1% less. The latter would hide a margin in the Reference Price, against ADR-0003. | One funded mainnet purchase before launch; poll MCP invoices through MCP `get-invoice-by-id`. |

### Web

| # | Finding | Fix |
|---|---|---|
| W1 | `send()` signs with whichever wallet is connected; if the user switched accounts in the wallet, Withdraw and limit changes are signed by a different account than the one shown. | Assert the signer matches the session; listen to the wallet's sign-in/out events. |
| W2 | Quote responses can arrive out of order, so the page can show one mode's price next to another; the buy request sends local mode with the quote's maximum. | Cancel stale quote requests; buy with `quote.mode`. |
| W3 | Voucher codes stay on screen after sign-out; an expired session is never detected (raw "Unauthorized"). | Clear state on sign-out or 401; key authenticated state on the account. |
| W4 | No CSP, `frame-ancestors`, nosniff or referrer policy on a wallet-connected app (clickjacking, token theft after any XSS). The token is in localStorage. | Security headers now; later an HttpOnly cookie on `.gamified.trade`. |
| W5 | Pending purchases never update; buys have no timeout. | Poll until settled; timeout the request. |
| W6 | Redemption links render any scheme; Draw Proof doesn't check the event's `executor_id`. | https-only links; filter receipts by `executor_id === contractId` and success. |

## P1: the startup surface

**Landing page and structure.** `/` is a search box today: no explanation of how it works, the modes, fairness, the Telegram agent, trust, or an FAQ. Proposed structure:

```
app/
  (marketing)/   server components, no wallet code
    page.tsx              landing: hero, how it works, modes + honest odds, fairness, Telegram, FAQ, footer
    fair/  draw/[tx]/     server-rendered, cached; client island only for the recompute
    terms/ privacy/ responsible-play/
  (app)/         SessionProvider + near-connect only here
    shop/ purchases/ wallet/
  not-found.tsx error.tsx robots.ts sitemap.ts
packages/contract/   contract view types, event schema, draw.ts shared by server and web
```

**Honest odds.** The copy leads with the rare outcome. "Classic: 4% chance to pay less" and "You pay at most $15.00, and maybe much less" never say that the likely result is paying the full premium (96% and 75% of the time). For trust, and for regulators, show the outcome split up front: *"Most likely: $15.00 (75%). Otherwise less, down to free."*

**Design and UX:**
- No feedback when opening a voucher (about 1s blank). No product images, though Bitrefill provides them. No preselected amount. 32px tap targets.
- No footer, support contact, socials or legal pages.
- The brand palette (ink, paper, gold) is used plainly: no logo mark, and the gold barely appears.
- `/fair` loads its numbers client-side (blank "—" first). Every page is titled "Luckout"; there's no robots.txt or sitemap.
- Sign-in assumes the visitor knows NEAR wallets; there's no first-time explanation.
- Each route ships about 290 KB of gzipped JS, including a 113 KB Effect client, even on `/fair` and `/draw`.

**Production basics:** error and not-found pages; analytics and error monitoring (Vercel Analytics plus Sentry); validated web env (a production build fails if a variable is missing); naming that matches CONTEXT.md (Running Total, Default Mode).

## P2: operations

- Alerts for operator gas and key allowance, Bitrefill float, contract NEAR balance, stuck purchases, and reconciler lag.
- Customer notifications when the reconciler finishes a purchase (Telegram DM).
- Off-VM backups and a tested restore.
- A runbook for stuck purchases.
- Telegram bot: concurrent updates, per-user rate limit, LLM timeouts.
- Tests:
  - State-machine tests on PGlite with fake Near and Bitrefill layers that inject a crash at each step.
  - Contract sandbox tests for `ft_transfer_call` refunds, callback gas, and the multi-action attack.
  - Money formatting tests on the web.
